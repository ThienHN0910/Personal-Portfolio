1. The 1GB RAM Dilemma: Avoiding Linux OOM-Killer Terminations

Cloud providers frequently offer low-spec virtual private servers under free-tier quotas (e.g., GCP e2-micro with 1GB RAM). In these environments, memory is the primary limiting resource. When an application log file grows to hundreds of megabytes, executing a naive Node.js read operation like fs.readFileSync('/root/.pm2/logs/app-error.log') buffers the entire file into the V8 JavaScript heap.

On a 1GB host running a web application, Node.js, and Nginx, this sudden heap spike pushes system memory utilization past the physical threshold. The Linux kernel responds by invoking the Out-Of-Memory Killer (oom-killer), immediately terminating the Node.js process and causing complete service downtime.

2. OOM-Safe Log Streaming via OS-Level Tail Piping

To guarantee that log inspections never consume V8 runtime heap, Dev Assistant Bot delegates log parsing directly to the Linux operating system kernel using a spawned tail -n 20 child process: 

import { spawn } from 'node:child_process';

export function streamTailLogs(logFilePath: string): Promise<string> {
  return new Promise((resolve, reject) => {
    // Spawns OS-level tail directly; Node.js never buffers the underlying log file
    const tail = spawn('tail', ['-n', '20', logFilePath]);
    let output = '';

    tail.stdout.on('data', (chunk) => {
      output += chunk.toString();
    });

    tail.stderr.on('data', (errChunk) => {
      console.error('Tail stderr:', errChunk.toString());
    });

    tail.on('close', (code) => {
      if (code === 0) {
        // Enforce Telegram message length limit (4096 characters)
        resolve(output.slice(-3800) || 'Log file is currently empty.');
      } else {
        reject(new Error(`tail exited with code ${code}`));
      }
    });
  });
}

By delegating file seeking to the Linux tail utility, the kernel seeks directly to the end of the file descriptor without loading historical log data into memory. The memory footprint inside Node.js remains constant at 0 MB overhead, regardless of whether the log file is 10 KB or 10 GB.

3. Multi-Target Deployment Pipeline & Smart Repo Inspector

Running builds (e.g. npm run build with Vite, Webpack, or Next.js) directly on a 1GB VPS will predictably cause memory exhaustion. To solve this, the orchestrator incorporates a Smart Repo Inspector that inspects the repository root and routes each application to its optimal platform:

  1. Pure Static Web (static_pure): Sites with root index.html requiring no compilation are deployed directly to VPS Nginx. Rather than executing a heavy git clone that duplicates Git history, the bot fetches a lightweight GitHub zipball and flattens the directory structure.
  2. Frontend SPAs (frontend_spa): React, Vue, or Vite SPAs are deployed directly to Vercel Cloud via REST API, completely offloading heavy compilation cycles away from the VPS host.
  3. Backend APIs (backend_api): Node.js/Express APIs are provisioned on Render or deployed locally on the VPS managed by PM2 behind an isolated internal port.
  4. Monorepos (monorepo): Automatically splits frontend and backend components, deploying the frontend to Vercel and backend to Render simultaneously.

4. Automated Cloudflare DNS Provisioning & Subdomain Routing

Each deployment dynamically provisions a custom subdomain (e.g., https://portfolio.thienhn.io.vn or https://test.thienhn.io.vn) by orchestrating Cloudflare API v4: 

// Excerpt from lib/providers/cloudflare.js
export async function createDnsRecord({ name, type, content, proxied = false }) {
  const url = `https://api.cloudflare.com/client/v4/zones/${process.env.CLOUDFLARE_ZONE_ID}/dns_records`;
  const response = await fetch(url, {
    method: 'POST',
    headers: {
      'Authorization': `Bearer ${process.env.CLOUDFLARE_API_TOKEN}`,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      type, // 'A' for VPS Public IP, 'CNAME' for Vercel/Render
      name: `${name}.${process.env.BASE_DOMAIN}`,
      content,
      ttl: 1, // Auto TTL
      proxied
    })
  });
  return response.json();
}

When an application is undeployed via /web_remove <name> or the Web Dashboard, the corresponding DNS record ID is retrieved and deleted immediately, ensuring no orphan records accumulate in the Cloudflare DNS zone.

6. Low-Overhead Performance Profiling (/perf)

Auditing web performance directly from a low-spec host typically encounters severe bottlenecks: running a headless Chromium browser for Lighthouse audits consumes > 500 MB RAM, freezing the server. Dev Assistant Bot resolves this via a dual-mode benchmarking engine:

  • In-Situ TTFB Breakdown via curl -w (0 MB RAM): Executes native curl with timing formatters, breaking down network latency with microsecond accuracy: 
    curl -s -w "DNS: %{time_namelookup}s | Connect: %{time_connect}s | TTFB: %{time_starttransfer}s | Total: %{time_total}s\n" -o /dev/null http://localhost:8081
  • Cloud Delegation for Lighthouse Audits: Instead of running local browser instances, /perf delegates mobile audits to the Google PageSpeed Insights API. Google's cloud infrastructure evaluates First Contentful Paint (FCP), Largest Contentful Paint (LCP), and Cumulative Layout Shift (CLS), returning structured metrics to the bot with 0 local CPU cost.

7. Security Hardening & PM2 RAM Ceiling

Because the bot executes administrative shell operations on the host, security and resource constraints are strictly enforced:

  • 200MB RAM Ceiling: Running with --max-memory-restart 200M ensures that any inadvertent memory leak causes a graceful daemon recycle rather than server kernel freeze.
  • Sender ID Whitelist Middleware: Every incoming Telegram update passes through authorization middleware comparing ctx.from.id against the configured AUTHORIZED_TELEGRAM_ID. Unauthorized interactions are dropped and logged.
  • Whitelisted Shell Runner: Arbitrary shell input is strictly prohibited. The /sh command accepts only pre-registered aliases defined in config/whitelist.js, eliminating Remote Code Execution (RCE) vectors.
  • Self-Healing Updates (/update): Pulls updates from GitHub, runs dependency updates, verifies syntax (npm run check:syntax), and triggers a clean PM2 process reload autonomously.
