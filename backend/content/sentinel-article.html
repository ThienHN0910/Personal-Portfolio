Sentinel began as a Discord bot and evolved into a multi-surface platform encompassing a live web dashboard, real-time community analytics, an interactive economy, and mini-games shared seamlessly between Discord and the browser. The core architectural challenge was determining authoritative state ownership: Discord messages are ephemeral, browser tabs can race each other, and bot restarts must never compromise currency balances or interrupt active wagers.

This architectural study examines the technical decisions powering the live Sentinel Case Study. It details how optimistic version locking, atomic escrow transfers, zero-trace confessions, and isolated OAuth sessions deliver a robust, tamper-resistant community platform.

1. Unifying Truth Across Discord Buttons and Web Interfaces

Discord interaction components (buttons, select menus) and Vue 3 frontend components communicate with the exact same backend service layer. A shared game session record maintains a 21-character alphanumeric session ID, guild ID, player references, current phase, deadline timestamp, and monotonic version number.

The service projects perspective-filtered responses after each turn: in Rock-Paper-Scissors, each participant's choice remains masked until both moves have been submitted; in Tic-tac-toe, turns and board coordinates are validated on the server. The client interface never calculates game logic or decides the victor independently.

2. Rejecting Stale Moves with Optimistic Database Locks

When two members interact with a game or place a wager simultaneously, a naive read-modify-write pattern would introduce classic lost-update anomalies. Sentinel prevents this by enforcing conditional optimistic locking at the MongoDB document boundary: 

// Optimistic Concurrency Control on Game State Transitions
const written = await GameSessionModel.findOneAndUpdate(
  { sessionId, version: state.version, expiresAt: { $gt: now } },
  { $set: nextFields, $inc: { version: 1 } },
  { new: true, lean: true }
);

if (!written) {
  throw new GameSessionError('conflict', 'Board state modified concurrently. Please reload.');
}

Under this contract, only the first request matching the expected version number succeeds. Any competing request receives an immediate conflict exception and re-synchronizes with the latest authoritative board state.

3. Atomic Escrow Settlements for the DNE Currency Economy

Sentinel introduces DNE Coins, an in-server virtual currency earned through active voice attendance, chat activity, daily check-in streaks, and weighted gacha rolls. When members enter 1v1 P2P wagers or community pool bets, allowing unreserved currency invites double-spend exploits.

To guarantee economic integrity, Sentinel implements an atomic Escrow Mechanism:

  • Phase 1 (Lock): When a wager is created or accepted, both participants' balances are atomically decremented via { $inc: { balance: -stake } } with a precondition filter { balance: { $gte: stake } }. The pooled funds are assigned to the wager document's escrow field.
  • Phase 2 (Resolution): Upon game completion, the victor receives the combined escrow sum in a single atomic credit operation.
  • Phase 3 (Abort / Refund): If a wager expires after its 15-minute timeout without completion, the escrowed funds are automatically refunded to the creators.

4. Zero-Trace Ephemeral Confessions & Virtual Pet Invariants

Online communities require spaces for honest feedback and vulnerability, but traditional confession bots frequently store author metadata in hidden logs, creating massive privacy liabilities. Sentinel solves this through an architectural Zero-Trace Guarantee:

Incoming confessions submitted via Discord modal dialogs or direct messages are sanitized in-flight, immediately dispatched to the server's configured confession channel via webhook, and completely dropped from memory. No author ID, user handle, or IP hash is ever persisted to database records or log files.

Simultaneously, Sentinel's Virtual Pet System enforces a humane Zero-Death Invariant. Pets never perish due to member inactivity. Instead of running expensive periodic polling jobs across tens of thousands of members, a pet's mood is computed lazily upon inspection based on elapsed time since the last recorded feeding timestamp:

5. Token Isolation & Live Data Provenance

Authentication for the web management panel uses Discord OAuth2. To prevent token leaks, Discord access tokens are exchanged server-side, used to verify ownership, and promptly discarded. The browser receives a secure, SameSite, HttpOnly cookie containing an opaque session token. MongoDB stores only the SHA-256 hash of the session token with an automated TTL expiration.

Furthermore, the public analytics dashboard enforces transparent data provenance: cumulative totals, 7-day rolling window heatmaps, and in-progress voice estimations are explicitly demarcated so viewers never mistake an active session estimate for a finalized historical benchmark.

Key Takeaways for Distributed Bot Engineering

Building a platform that spans chat gateways and web frontends requires decoupling domain state machines from transport protocols. By enforcing optimistic concurrency at the database layer, isolating third-party authentication tokens, and providing clear guarantees around privacy and currency escrow, developers can build interactive community experiences that remain fast, entertaining, and mathematically consistent.
