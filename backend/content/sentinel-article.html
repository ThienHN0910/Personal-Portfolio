Sentinel began as a Discord bot and grew into a web dashboard with games that can be played from either interface. The hard part was deciding which process owns truth: Discord messages are transient, browser clients can race each other, and a bot restart must not erase an unfinished game or reminder.

This is an implementation study of the live Sentinel Case Study. It describes decisions visible in the source code and production UI; screenshot values are examples from one server, not claims about scale or performance.

1. Give every surface the same source of truth

Discord message components and Vue buttons both call the same game service. A game record has a 21-character session ID, guild ID, two player IDs, phase, expiry, and version. The service projects a viewer-specific response after each action. Rock-paper-scissors choices stay hidden until both players have submitted them; tic-tac-toe records its board and turn. The browser never decides the winner on its own.

A waiting game expires after 15 minutes. An active game extends its deadline after valid activity and expires after 30 minutes of inactivity. Finished records are retained briefly for result display, then MongoDB TTL cleanup removes them. An active-key constraint prevents one creator from opening multiple unfinished games in the same guild.

2. Reject stale moves at the database boundary

Two users can click at nearly the same time. Reading a document, changing it in memory, and saving without a condition would let the later write erase the earlier move. Sentinel instead validates the rule against the loaded state, then issues a conditional MongoDB update matching the previous version and an unexpired deadline:

const written = await GameSessionModel.findOneAndUpdate(
  { sessionId, version: state.version, expiresAt: { $gt: now } },
  { $set: nextFields, $inc: { version: 1 } },
  { new: true, lean: true }
)
if (!written) throw new GameSessionError('conflict', 'Reload game state')

This is optimistic concurrency: only one update based on a given version can succeed. The loser receives a conflict and can reload the latest board. A separate guarded update binds a web-created session to a Discord message for the game-open command, so reposting does not create two authoritative messages.

3. Treat authentication and guild permission as different questions

Discord OAuth2 signs a person in with the identify and guilds scopes. The API creates a short-lived, single-use state value to protect the callback, exchanges the code on the server, and discards the Discord access token after creating a session. The browser receives a secure, HttpOnly, SameSite cookie; MongoDB stores only a hash of its opaque session token with a TTL expiry.

A valid session answers who is this user? It does not grant permanent rights to change every guild. Administrative routes re-check that the bot is in the guild and that the caller currently owns it or has Manage Server permission. Game actions likewise verify membership and player identity. This keeps a saved browser session from becoming stale authority after a Discord role changes.

4. Make dashboard numbers traceable

The public dashboard obtains guilds and statistics from Fastify routes. It refreshes at 30-second intervals, and the API caches each dashboard snapshot for 30 seconds to avoid repeating expensive aggregation for every viewer. Its seven-day heatmaps and cumulative totals are labelled separately. Voice time already persisted is distinct from the estimate for people currently in voice.

The landing dashboard features a short podium. The full ranking route pages through chat, stored voice time, and level rather than shipping every user in a single response. A server selector changes the API URL and result set. This is also an editorial constraint: a screenshot can show what production looked like at capture time, but the page itself must always read current data.

5. Keep background delivery bounded

The reminder command stores a private DM reminder with a due time and status. A polling service checks due items every 30 seconds, while per-user limits prevent an unbounded queue. Delivery failures remain visible to the creator, and terminal records expire after seven days. Voice tracking is also reconciled periodically so a missed Gateway event does not leave an active session open forever.

What I would carry forward

The useful pattern is to place domain decisions in services that both Discord and HTTP adapters call, and to enforce the final concurrency check where data is written. A second lesson is to make data provenance visible: cumulative totals, seven-day activity, and in-progress estimates should never share an unlabeled number.
